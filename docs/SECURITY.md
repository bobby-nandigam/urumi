# Security model

A short, defensible account of how the platform protects itself.

## Credentials & authentication

- **API keys** (`urumi_<prefix>_<secret>`) are the single credential for both the
  MCP data plane and the dashboard. They are generated with a CSPRNG, shown to
  the operator **once**, and stored only as a **bcrypt hash** alongside a
  searchable prefix. A leaked database yields no usable keys.
- **Revocation** is a soft-delete (`revoked_at`): revoked keys stop
  authenticating immediately but remain referenced by historical audit rows.
- **No secrets in source.** Store credentials, the WooCommerce REST key, the
  Postgres password, and the agent's gateway key all live in Kubernetes
  Secrets. The charts carry only dev placeholders; production values are
  supplied at install time. The Postgres password is generated by the chart and
  preserved across upgrades via a Helm `lookup`.

## Authorization

- Three roles: `admin` (all tools + management), `member` (all tools), `viewer`
  (read-only tools only).
- Tool-level authorization is driven by each tool's MCP `readOnlyHint`
  annotation, evaluated at the gateway. A `viewer` key cannot even *see* a
  write tool in `tools/list`, and a direct call is rejected and audited as
  `denied`.
- The dashboard/management API additionally requires the `admin` role.
- The chat agent holds a **member** key — least privilege: it can drive tools
  but cannot mint or revoke keys.

## Auditing

Every tool call — allowed, denied, or errored — is written to `audit_log` with
the key, role, tool, upstream, arguments, outcome, and duration. This is the
tamper-evident record of who did what through the gateway.

## Workload hardening

Every container runs with:

- `runAsNonRoot: true` and an explicit non-root UID.
- `allowPrivilegeEscalation: false`, all Linux capabilities dropped, and the
  `RuntimeDefault` seccomp profile.
- A **read-only root filesystem** where the workload allows it (gateway, agent,
  woo-mcp, utils-mcp), with writable `emptyDir`s only for `/tmp`.

## Network exposure

- Only `store`, `dashboard`, `gateway`, and `agent` have Ingress. The MCP
  servers (`woo-mcp`, `utils-mcp`) and Postgres are **ClusterIP only** — never
  reachable from outside the cluster.
- The gateway `/mcp` endpoint is internet-facing (for external MCP clients) but
  is useless without a valid Bearer key.
- In production, Traefik terminates TLS via cert-manager (configured in the
  `values-prod.yaml` ingress annotations).

## Known trade-offs (local/dev)

- The in-cluster WooCommerce SSL shim (`X-Forwarded-Proto: https` →
  `is_ssl()`) is acceptable because in-cluster traffic is trusted and not
  TLS-terminated per hop; a production hardening step would be mTLS or a service
  mesh between the MCP server and the store.
- Single-replica Postgres with a PVC is right for this scope; a real deployment
  would use a managed or replicated Postgres.
- The first-boot bootstrap admin key is printed to logs; rotate it (mint real
  keys, revoke the bootstrap key) immediately after first login.
